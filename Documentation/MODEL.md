# SQLInsight — Machine-Learning Model

This document describes the SQLInsight detector end to end: preprocessing, feature
engineering, the classifier and its hyperparameters, the experimental results, a
comparison against the thesis and the approaches it cites, how to retrain, and the
known limitations. All numbers are quoted directly from
[`ml/artifacts/metrics.json`](../ml/artifacts/metrics.json), generated by
`ml/train_model.py`.

The model is a **scikit-learn `LogisticRegression`** over a **`CountVectorizer`
feature union** — faithful to the thesis pipeline (CountVectorizer +
VarianceThreshold + LogisticRegression), with targeted accuracy- and
generalisation-oriented improvements described below.

---

## 1. Pipeline overview

```
Query string
   │
   ▼
load_dataset()                 # ml/preprocess.py — clean & normalise {Query,Label}
   │
   ▼
FeatureUnion                   # ml/preprocess.py — build_vectorizer()
   ├── word   CountVectorizer  # SQL-aware tokens, 1–2 grams
   └── char   CountVectorizer  # char_wb, 3–5 grams
   │
   ▼
VarianceThreshold(0.0)         # drop constant/zero-variance columns
   │
   ▼  (80,650 features)
LogisticRegression             # C=4.0, liblinear, max_iter=1000, class_weight=balanced
   │
   ▼
P(malicious) ≥ 0.5  →  verdict
```

The fitted vectorizer (a `Pipeline`) is saved **separately** from the classifier —
`vectorizer.joblib` and `ML_model.pkl` — matching the thesis deployment that loads
the model and a vectorizer artifact independently and runs
`model.predict(vectorizer.transform([query]))`.

---

## 2. Preprocessing — `ml/preprocess.py:load_dataset()`

Both datasets are `{Query, Label}` CSVs. `load_dataset()`:

1. Reads with `encoding="utf-8", encoding_errors="replace"` — the raw datasets
   contain non-UTF-8 bytes, so this prevents decode crashes (see [DATASET.md](DATASET.md)).
2. Normalises column names to `Query` / `Label` (case-insensitive match, falling
   back to first/last column).
3. Casts `Query` to string; drops rows with NA or empty/whitespace-only queries.
4. Coerces `Label` to numeric, drops un-parseable labels, casts to `int`.

This mirrors the thesis cleaning stage (drop empties/duplicates, standardise format,
`dropna`) while being robust to messy real-world CSV bytes.

## 3. Feature engineering — `ml/preprocess.py:build_vectorizer()`

Two `CountVectorizer` instances combined with `FeatureUnion`, then a
`VarianceThreshold`:

### Word features (SQL-aware)
```python
CountVectorizer(
    lowercase=True,
    token_pattern=r"(?u)\b\w+\b|[^\w\s]",   # SQL_TOKEN_PATTERN
    ngram_range=(1, 2),
    min_df=2,
    max_features=50_000,
)
```
The token pattern matches either a word/identifier **or any single non-word,
non-space character** — so `'`, `"`, `-`, `=`, `;`, `(`, `)` survive as tokens. The
default scikit-learn tokenizer (`\b\w\w+\b`) discards exactly this punctuation, yet
it carries the strongest injection signal (`' or 1=1 --`, `union select`,
`; drop`). The 1–2 gram range lets discriminative bigrams like `union select` form.

### Character features
```python
CountVectorizer(
    lowercase=True,
    analyzer="char_wb",
    ngram_range=(3, 5),
    min_df=3,
    max_features=60_000,
)
```
Character n-grams (3–5, word-boundary aware) capture the *syntactic fingerprint* of
injection payloads independent of exact tokenisation, which generalises far better
to unseen / obfuscated attacks than word tokens alone.

### Variance threshold
```python
VarianceThreshold(threshold=0.0)
```
Keeps the thesis's feature-reduction stage but uses `threshold=0.0` (drop only
constant / zero-variance columns). The thesis value
`VarianceThreshold(.0001 * (1 - .0001))` would, with `min_df` already filtering rare
terms, also drop discriminative 2-document bigrams such as `union select`, hurting
recall — so the stage is preserved without that side effect.

The fitted union produces **80,650 features** (`metrics.json → features.n_features`).

### Why this beats the thesis's plain CountVectorizer

The thesis uses a single word-level `CountVectorizer` (default token pattern) +
`VarianceThreshold`. SQLInsight improves generalisation and accuracy in three ways:

1. **SQL-aware tokenisation** keeps injection punctuation that the default tokenizer
   throws away — recovering the most discriminative single characters and short
   sequences.
2. **Character n-grams** model sub-token structure, so novel payloads that reuse
   familiar fragments (`=`, `--`, `0x`, `sleep(`) are still recognised — directly
   addressing the thesis's own concern about generalising to evolving attacks.
3. **A tuned `VarianceThreshold`** retains rare-but-decisive bigrams instead of
   pruning them.

The net effect is a higher held-out F1 **and** a materially better honest
generalisation number than the thesis baseline (Section 5).

## 4. Classifier — `ml/train_model.py`

```python
LogisticRegression(C=4.0, solver="liblinear", max_iter=1000, class_weight="balanced")
```

| Hyperparameter | Value | Rationale |
|----------------|-------|-----------|
| `C` | `4.0` | Lighter L2 regularisation; the high-dimensional sparse feature space benefits from a less-constrained fit. |
| `solver` | `liblinear` | Efficient for high-dimensional sparse binary problems; supports the default L2 penalty. |
| `max_iter` | `1000` | Headroom to converge on ~80k features. |
| `class_weight` | `balanced` | Re-weights classes inversely to frequency, important because the training set is imbalanced (≈63% benign / 37% malicious). |

Logistic regression is the thesis's chosen model: simple, interpretable, fast, and
strong on binary text classification — a good accuracy/compute trade-off versus
deep models.

### Decision threshold
Inference (`backend/detection.py`) applies `THRESHOLD = 0.5` on `P(malicious)` — the
natural logistic-regression boundary, validated to catch the canonical attack
classes while holding precision around 98.5% on unseen data.

### Training procedure
1. Fit the feature pipeline on the **full** training corpus
   (`Modified_SQL_Dataset.csv`).
2. **Experiment 1:** 80/20 *stratified* split (`train_test_split`,
   `random_state=42`) → evaluate on the held-out 20%.
3. **Deployed model:** refit `LogisticRegression` on **100%** of the training data
   (this is what ships in `ML_model.pkl`).
4. **Experiment 2:** evaluate the deployed model on the generalisation dataset
   (`clean_sql_dataset.csv`), reported two ways (full and unseen-only).

## 5. Results

Source: `ml/artifacts/metrics.json` (sklearn `1.8.0`; 80,650 features). Metrics are
percentages; confusion-matrix counts are absolute.

### Experiment 1 — within-distribution (held-out 20% of `Modified_SQL_Dataset.csv`)

| Metric | Value |
|--------|------:|
| Accuracy | **99.71%** |
| Precision | **99.96%** |
| Recall | **99.25%** |
| F1-score | **99.60%** |
| Test samples | 6,184 |
| Train samples | 24,734 |

Confusion matrix (test set, n = 6,184):

| | Predicted benign | Predicted malicious |
|---|---:|---:|
| **Actual benign** | TN = 3,907 | FP = 1 |
| **Actual malicious** | FN = 17 | TP = 2,259 |

Essentially one false positive across 3,908 benign queries.

### Experiment 2 (unseen-only) — the honest generalisation number

**Important finding.** The training set (`Modified_SQL_Dataset.csv`) is ~entirely
contained within the evaluation set (`clean_sql_dataset.csv`) — roughly 20.8% of the
clean dataset's rows are exact training queries. Reporting on the full clean set
therefore re-scores rows the model has already seen and inflates the result. We
report **both** the thesis-style "full" number (above) **and** the honest
**unseen-only** number, which excludes every clean-dataset query that appears in the
training set (≈79% of the clean set, 117,346 rows):

| Metric | Value |
|--------|------:|
| Accuracy | **90.35%** |
| Precision | **98.49%** |
| Recall | **84.23%** |
| F1-score | **90.80%** |
| Samples | 117,346 |

Confusion matrix (unseen-only, n = 117,346):

| | Predicted benign | Predicted malicious |
|---|---:|---:|
| **Actual benign** | TN = 50,138 | FP = 859 |
| **Actual malicious** | FN = 10,461 | TP = 55,888 |

The honest unseen-only accuracy (90.35%) is the number to cite for real-world
generalisation. It is conservative and still **beats the thesis's second-experiment
baseline of 84.51%**.

> Methodology note: this train-in-eval contamination is itself a finding. The
> thesis's Experiment 2 evaluates on a dataset that overlaps its training data;
> SQLInsight surfaces that overlap explicitly and reports the de-duplicated number
> so the generalisation claim is defensible to a committee.

## 7. Retraining

```bash
python ml/train_model.py
```

This:
1. Loads `data/Modified_SQL_Dataset.csv` (train) and `data/clean_sql_dataset.csv`
   (eval) via `ml/preprocess.py:load_dataset()`.
2. Fits the feature pipeline; runs Experiment 1 (80/20 split); refits the final
   model on 100% of training data; runs Experiment 2 (full + unseen-only).
3. Writes the three artifacts to `ml/artifacts/`:
   - `ML_model.pkl` — the deployed `LogisticRegression`.
   - `vectorizer.joblib` — the fitted feature `Pipeline`.
   - `metrics.json` — all metrics + metadata (sklearn version, params, feature
     count, dataset rows, the three experiments, and a `headline` block).

`random_state=42` makes Experiment 1's split reproducible. Training takes on the
order of seconds-to-a-minute on a modern laptop.

### How the artifacts are consumed
- **`backend/detection.py`** loads `ML_model.pkl` + `vectorizer.joblib`
  (`functools.lru_cache`, so once per process) and serves every `detect()` call.
- **`backend/app.py`** serves `metrics.json` verbatim at `GET /api/model`, and folds
  the `headline` + `experiment_2_unseen` blocks into `GET /api/stats` for the
  dashboard's model panel.

> **Version pinning.** `requirements.txt` pins `scikit-learn==1.8.0` — the exact
> version the committed artifacts were trained with — so the pre-trained pickle loads
> cleanly without retraining. If you retrain on a different scikit-learn version,
> keep the pin and the artifacts in sync.

## 8. Limitations

Echoing the thesis's *Challenges and Limitations* (Section 6.5) and consistent with
the measured results:

- **Recall on unseen data.** On the unseen-only set, recall is 84.23% (FN = 10,461):
  some genuinely malicious queries are missed. This is the central
  precision/recall trade-off in IDS — the deployed threshold (0.5) favours precision
  (~98.5%) to avoid blocking legitimate traffic, which means more false negatives.
  Lowering the threshold would raise recall at the cost of more false positives.
- **Dataset quality and coverage.** The thesis notes datasets were "insufficient or
  not up-to-date" and that aggressive filtering deleted useful entries. The benign
  class here is short free-text user inputs (usernames, addresses, numbers), so the
  model learns "looks like SQL/punctuation-heavy ⇒ malicious"; payloads engineered to
  look like ordinary text, or benign inputs that legitimately contain SQL-like
  tokens, are the hard cases.
- **Evolving attack techniques.** Static training data cannot anticipate novel
  obfuscation. Character n-grams help generalise, but periodic retraining on fresh
  data is required to keep pace.
- **Scope.** Like the thesis, SQLInsight only **detects and alerts** on SQL
  injection — it does not prevent or remediate, and it inspects only server-side
  query strings (not client-side activity, cookies, or full HTTP bodies). Future work
  (per the thesis) includes covering XSS/other attack classes and a firewall
  integration API for automatic IP blocking.
